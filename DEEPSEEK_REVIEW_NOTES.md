## Не исправлено до конца

### 12) Поддержка RRF 2.x всё ещё хрупкая
**Где:** `duet_client.py`

Для RRF 2.x код всё ещё делает примерно следующее:
- отправляет `GET /rr_gcode?gcode=M114`;
- сразу пытается распарсить ответ как координаты.

**Проблема:** это всё ещё слишком оптимистичное предположение. Для семейства `rr_*` у RepRapFirmware historically есть нюансы с:
- сессиями;
- reply-механикой;
- форматом ответа;
- различиями между версиями.

**Что это значит practically:**
mock-режим и локальные тесты не доказывают, что это будет надёжно работать на реальной Duet 2 с RRF 2.x.

**Что нужно сделать:**
- либо сузить обещанную поддержку и честно зафиксировать ограничения;
- либо реализовать и проверить корректный сценарий получения ответа для RRF 2.x;
- либо добавить реальные интеграционные проверки на целевой прошивке.

### 13) Модель HTTP-сессий RepRapFirmware всё ещё реализована упрощённо
**Где:** `duet_client.py:connect`, `_request`

**Проблема:**
клиент по-прежнему не реализует полноценную сессионную модель Duet API:
- нет явной логики восстановления после `401`;
- нет отдельной обработки `503` как состояния платы;
- не видно чёткого login/reconnect flow для всех режимов.

**Почему это важно:**
если появится пароль, потеря сессии или нестабильный ответ платы, клиент может вести себя хуже, чем ожидает пользователь.

**Вывод:** это не «косметика», а реальное остаточное ограничение интеграции.

## Новые/дополнительные замечания

### 14) `api_connect` смешивает пользовательские ошибки и ошибки платы в HTTP 502
Сейчас `ValidationError` и `DuetError` в `/api/connect` сводятся к одному статусу `502`.

**Почему это плохо:**
- некорректный IP/hostname со стороны пользователя — это скорее `400`;
- реальная ошибка общения с платой — это `502`.

**Что исправить:**
разделить ответы по типу ошибки.

### 15) Тестов всё ещё недостаточно для заявления о полной надёжности
Сейчас тесты есть, и это хорошо. Но не покрыты важные сценарии:
- превышение `max_step_mm`;
- превышение `speed_mm_min`;
- отказ при не-homed оси;
- проверка `min_position` / `max_position`;
- проверка allowlist raw G-code при включённом endpoint;
- валидация плохих макросов;
- негативные сценарии `config.json`.
